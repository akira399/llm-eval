# 版本回归对比报告 · Poke-RAG v1 → v3

- 评测平台：LLM-Eval（[技术方案](../docs/00-技术方案.md)）
- 用例集：`cases/poke-rag-v0.yaml`（50 条 × 10 类目，v1/v2/v3 完全同一套）
- 被测系统：Poke-RAG（BM25-only + deepseek-v4-flash，temperature 0.2）
- AI 裁判：deepseek-v4-flash temperature 0（细则经 M1 一轮校准，人工一致率 98%/Kappa 0.935）
- 对比运行：`runs/bm25-baseline-final.jsonl`（v1）→ `runs/bm25-v2-*.jsonl` → `runs/bm25-v3-*.jsonl`

## 1. 三个版本的改动内容

| 版本 | 改动 | 依据 |
| --- | --- | --- |
| v1（基线） | — | 首轮 50 条评测 + 人工盲评 |
| v2 | ①上下文组装白名单补 meta/typechart（v1 的 Meta 类卡片被静默丢弃）；②属性克制知识入检索语料（每防守属性一张卡） | v1 归因：Meta 4/4、属性克制 4/4 全败，根因定位到组装层与语料缺口 |
| v3 | 克制卡补「攻击视角」段落（克制谁/被谁抵抗/对谁无效） | v2 归因：tc-003/004 定位到生成层，实为知识表达缺口——模型如实指出"片段只有防守视角" |

## 3. 分类目正确性对比（关键类目）

| 类目 | v1 | v2 | v3 | 说明 |
|---|---|---|---|---|
| 对战环境 Meta | **0.0** | 0.833 | **0.875** | 组装修复后从全败到可用；剩余 0.125 是卡片缺少分级定义（见 §5） |

## 4. 自动化归因对账（scripts/attribute.py）

| 运行 | 失败数 | 归因分布 |
|---|---|---|
| v1 | 9 | 检索/组装层 8（tc×4、meta×4）+ 无法自动定位 1（hard-003 多跳题） |
| v2 | 3 | 生成层 2（实为攻击视角知识表达缺口）+ 无法自动定位 1 |
| v3 | 3 | 全部为已知的 hard/知识边界问题（见 §5） |

v1 的归因输出与人工诊断逐条吻合；v2 的"生成层"标签引导发现了第三处修复点——
归因工具不只是打标签，它在驱动修复路线。

## 5. 方差与剩余问题（如实报告）

1. **单次评测存在回答方差**：hard-001 在 v1/v3 的回答都是诚实拒答、未编造数值
   （忠实度均为满分），但 v1 解释了"缺少伤害公式与能力值"（按细则判覆盖），
   v3 只说了"无法计算"（判不覆盖）。这说明 hard 类用例单次跑分有波动，
   结论应以多轮评测或更大用例集为准——这也是 M3 扩写到 200 条的动机之一。
2. **meta-004（Ubers 定义）**：使用率卡片不含分级规则说明，模型如实说
   "未找到规则定义"并从数据列举了传说宝可梦。修复方向：meta 卡片补充分级定义段。
3. **hard-003（多跳配招建议）**：需要"宝可梦×环境×道具"跨卡推理，当前知识组织
   不支持，三个版本一致失败——如实标注为已知边界，不粉饰。
4. 裁判本身偶发空响应（v2 的 meta-003）：平台按 fail-visible 原则记 None 而非
   编造分数，v3 重判正常。

## 6. 方法论沉淀

- **评测 → 归因 → 修复 → 复测**的闭环在本轮完整走通，三轮共发现并修复 3 处
  知识/工程缺口，每处修复前都有归因证据、修复后都有同用例集量化验证。
- 修复时引入过一次检索污染（卡片正文堆砌查询词导致 78 问评测 top-3 99%→94%），
  靠自带的回归评测当场抓住并回退——**被测系统自身的评测与平台评测互为保险**。
