# LLM-Eval · LLM 应用效果评测与回归平台 技术方案

> 项目三：给 LLM 应用装上「效果仪表盘」——改提示词/换模型/调检索参数之前，
> 先用同一套用例集跑一遍，用数字说话：变好了还是变坏了、问题出在检索还是生成。

## 0. 一句话定位

以自研的 Poke-RAG（宝可梦对战知识库问答）为首个被测对象，构建
**用例集管理 → 自动化运行 → LLM-as-Judge 四维评分 → 版本回归对比 → 失败归因**
的完整评测闭环。所有评测结论可复现、可审计。

## 1. 为什么做这个

解决的真实痛点（AI 应用质量保障团队的日常）：

| 痛点 | 本平台的回答 |
| --- | --- |
| 改一句提示词，不知道变好还是变坏 | 版本回归对比：同一用例集并行跑 v1/v2，输出差异表 |
| 上线后被投诉"AI 编造"，说不清哪里错 | 失败归因：两级定位（检索没找到 vs 生成不忠实） |
| 没有评测集，验收靠"我感觉行" | 用例集管理 + LLM 自动扩写 + 人工抽检沉淀 |
| "AI 裁判"本身可信吗 | Judge 与人工标注做一致性比对，输出一致率 |

## 2. 总体架构

```
用例集 cases/*.yaml（查询 + 参考要点 + 期望行为）
        │
        ▼
   Runner（顺序/并发运行，记录每次原始输出 → runs/*.jsonl）
        │
        ▼
 被测应用适配器 providers/pokerag.py        ←—— 「版本」= 被测系统的配置快照
   （进程内调用 RAGEngine，或 HTTP 调 FastAPI）
        │
        ▼
   Judge（四维评分）
   ├─ 正确性   LLM 裁判：逐条核对参考要点
   ├─ 引用忠实度 LLM 裁判：断言是否被引用片段支持
   ├─ 格式     规则判定：引用编号、长度、模板残留（确定性、零成本）
   └─ 语气     LLM 裁判：简洁/专业/中文
        │
        ▼
 汇总与报表（summary.json + 对比表；M1 起 Streamlit 可视化）
```

关键设计决策：

1. **适配器模式**：被测应用不侵入。Poke-RAG 通过「进程内适配器」调用
   `RAGEngine().answer()`（无需起服务），另备 HTTP 模式走 `/api/chat` SSE，
   适配任意可 HTTP 化的 LLM 应用。
2. **版本 = 配置快照**：不 fork 代码做 v1/v2，而是给被测应用注入配置覆盖
   （如 `use_dense`、`top_k_answer`、temperature）。运行元数据记录生效配置，
   保证回归对比可复现。
3. **评分先规则后 LLM**：能用确定性规则判定的（格式、拒答行为）不花 LLM 成本；
   LLM 裁判只做真正需要语义理解的（正确性、忠实度、语气）。
4. **原始结果全部落盘**（jsonl）：评分可以事后重跑/换裁判模型，运行不用重跑。

## 3. 核心数据模型

### 3.1 用例（cases/*.yaml）

```yaml
- id: dex-001                # 类目前缀 + 序号，全库唯一
  category: 图鉴              # 类目用于分类目统计
  query: 快龙是什么属性的宝可梦？
  expect: answer             # answer=应作答 / reject=应承认不知道 / safe=不得越界(含注入)
  difficulty: easy           # easy | hard（hard 标注已知弱项，用于回归观察）
  key_facts:                 # LLM 裁判的核对要点（reject/safe 类可省略）
    - 回答指出快龙是龙属性和飞行属性
  notes: ""                  # 人工备注（如"人工抽检重点"）
```

阶段 0 种子集 `poke-rag-v0.yaml` 共 50 条，类目标签 10 个（超范围与安全同组考核）：
图鉴(10)、招式(9)、特性(6)、道具(6)、属性克制(4)、招式集合-规则工具(3)、
对战环境 Meta(4)、超范围(4)+安全(1)、伤害与配招-已知弱项(3)。

### 3.2 运行记录（runs/{version}-{时间戳}.jsonl）

每行一个用例的完整记录：用例字段 + 被测输出（answer_text、引用映射、
引用片段原文、是否拒答、citations_ok、耗时）+ 各维评分 + 判分理由。
评分与运行分离：重跑 Judge 不需要重跑应用。

### 3.3 汇总（summary.json）

总数/作答数/拒答数/错误数、耗时均值、四维均分、**分类目拆分**——
"检索类问题 95 分、Meta 类 60 分"这种粒度才是能指导改动的报告。

## 4. 评测维度定义

| 维度 | 判定方 | 分值 | 判定逻辑 |
| --- | --- | --- | --- |
| 正确性 correctness | LLM 裁判 | 0~1 | 逐条核对 key_facts，得分 = 覆盖要点数 / 要点总数 |
| 引用忠实度 faithfulness | LLM 裁判 | 0~1 | 把被引用的知识片段原文给裁判，检查回答中的断言是否被片段支持；无引用的回答按"存在无依据断言"计 |
| 格式 format | 规则 | 0~1 | 作答类：非空、≤800 字、引用编号 [n] 与引用映射一致；拒答类：含明确"无法回答/未找到"表述、≤400 字、不得编造答案 |
| 语气 tone | LLM 裁判 | 0~2 | 2=简洁友好专业中文；1=可接受有小瑕疵；0=啰嗦/答非所问的语气/模板腔 |

拒答类与安全类（expect=reject/safe）不参与"正确性"的要点核对，其正确性
退化为规则判定：不编造 + 礼貌说明边界。安全类额外断言：不得泄露系统提示词。

## 5. Judge 可信性验证（M1 核心）

"AI 裁判可信"不能自说自话，协议：

1. 从 50 条用例的回答中分层抽样 30 条（含满分/低分/拒答各档）；
2. 人工盲评：不看 AI 分数，按同一份评分细则独立打分；
3. 计算人机一致率与 Cohen's Kappa（kappa ≥ 0.6 记为"中等以上一致"）；
4. 把不一致样本的分歧原因归类（细则模糊 / 裁判偏置 / 用例问题），
   修订评分细则后复测——这正是评测工程师的日常工作流。

工具化实现（`scripts/annotate_app.py` 标注界面 → `runs/annotations/*.jsonl`
→ `scripts/agreement.py` 计算），盲评界面默认隐藏 AI 分数与理由。

分箱规则（人工自然语言档位 ↔ AI 分数，见 evalkit/agreement.py）：
正确性 对/部分对/错 ↔ ≥0.75/0.25~0.75/<0.25；忠实度 没有编造/有嫌疑/明显编造
↔ ≥0.9/0.5~0.9/<0.5；格式 没问题/有问题 ↔ ≥0.75/<0.75；语气 好/一般/差 ↔ 2/1/0。

## 6. 失败归因（两级定位）

对一个低分回答，按顺序回答两个问题：

1. **检索层**：被引用/检索到的片段里有没有能回答问题的内容？
   （数据来源：运行记录里保存的检索 top-k + 置信度）
   → 没有却硬答 = **检索失败**（该拒答没拒答）；
2. **生成层**：片段里有答案，回答却写错/漏写/编造
   → **生成失败**（提示词约束或模型能力问题）。

输出归因标签 + 证据引用，汇总进报告的「问题清单」，
作为被测应用的改进路线图（例如：M2 将发现"伤害计算类问题聊天路由未接入"）。

## 7. 版本回归对比

```
scripts/run_eval.py --cases cases/poke-rag-v0.yaml --version bm25-baseline
scripts/run_eval.py --override '{"rag": {"top_k_answer": 8}}' --version topk8
scripts/summarize.py runs/bm25-baseline-*.jsonl runs/topk8-*.jsonl
```

同一用例集、两个版本，输出逐维度/逐类目对比表与"新增失败用例清单"。
M2 目标：跑出一组真实数字（如"top_k 5→8 后正确性 +X%、平均耗时 +Y ms"）。

## 9. 目录结构与运行

```
llm-eval/
├── cases/            # 用例集（yaml，入库）
├── docs/             # 方案与讲解文档
├── evalkit/          # 平台核心包（schema/config/llm/judge/runner/providers）
├── promptfoo/        # promptfoo 配置与转换出的测试文件
├── runs/             # 运行产物（gitignore）
├── scripts/          # run_eval.py / summarize.py / export_promptfoo_tests.py
└── tests/            # pytest
```

运行环境复用 `poke-rag/.venv`（被测系统同解释器，避免双份依赖）：

```bash
PY=../poke-rag/.venv/Scripts/python.exe   # Windows Git Bash 写法

# 冒烟：跑 3 条（不含 LLM 裁判）
$PY scripts/run_eval.py --limit 3 --no-judge
# 全量 50 条 + 四维裁判（DeepSeek，成本约几分钱）
$PY scripts/run_eval.py
$PY -m pytest tests/ -q                   # 单元测试

# M1 工具链
$PY -m streamlit run scripts/annotate_app.py        # 人工盲评标注（判"AI 裁判可信"）
$PY scripts/agreement.py                            # 一致率 + Kappa + 分歧清单
$PY -m streamlit run scripts/show_report.py --server.port=8502   # 可视化报表
$PY scripts/make_report.py                          # 生成 Markdown 评测报告（reports/）
```

## 10. 风险与对策

| 风险 | 对策 |
| --- | --- |
| LLM 裁判不稳定 | temperature=0；要点核对改为逐条判定再聚合；关键场景与人工标注比对 |
| 裁判成本 | 规则维度零成本；50 条 ×3 次调用 ≈ 几分钱（DeepSeek 价位） |
| Meta 类无标准答案 | 参考要点写成宽松事实（给出具体名称+引用），标注"人工抽检重点" |
| 已知弱项污染均分 | difficulty=hard 用例单独统计，不与 easy 混算 |
| 机器资源受限 | 进程内调用无服务开销；评分结果落盘可离线重算 |

## 11. 泛化与产品化路线（Phase 0/1 已落地，2026-09-13）

原方案（§1-§10）完成于 Poke-RAG 单一被测对象。服务化审查（架构评审 + MCP 评审）结论：
现有仓库是"可复现的本地评测工具包"，可泛化的核心是**适配器协议、评分/运行分离、
规则优先、人工校准方法论**；被 Poke-RAG 写死的部分必须下沉为"能力扩展"。

### 11.1 Phase 0：通用核心契约（已完成）

| 新模块 | 职责 |
| --- | --- |
| `evalkit/contracts.py` | InvocationRequest / TargetObservation / EvaluationCase / TargetAdapter 通用契约；generic 套件加载器；新旧契约互转（RAG 流水线原样保留作回归基线） |
| `evalkit/judge_profile.py` | 评分即配置：规则评分器（要点覆盖/边界/JSON Schema/字段核对）+ 可选 LLM 评分器（语气/相关性）+ RagJudgeProfile 包装旧四维；异常记 score=None |
| `evalkit/engine.py` | EvaluationEngine 通用执行路径，产物与旧 Runner 同形（报表/对比/归因零改动复用）；单条异常隔离；进度回调 |
| `evalkit/demo.py` + `registry.py` | 两个离线确定性演示应用（聊天/JSON 抽取）+ 目标注册表（只收已注册 target_id） |

验收证据：新引擎经 PokeRagAdapter 跑真实 Poke-RAG 与旧路径四维均分完全一致；
demo 套件预埋缺陷被 Schema/字段评分器抓出；`runner.summarize` 改动态维度收集。

### 11.2 Phase 1：本地 stdio MCP 服务（已完成）

- `evalkit/service.py`：EvalService —— Web/CLI/MCP 共用唯一业务入口；
  SQLite 持久化 Job（状态机 queued/running/succeeded/partial/failed + 进度 + 幂等键）；
  套件仓库（内容 SHA-256 寻址）；预算硬限制（BUDGET_EXCEEDED）；
  未注册目标拒绝（TARGET_NOT_REGISTERED）。
- `mcp_server/`：9 个工具（list_suites/get_suite/list_targets/start_run/get_job/
  list_jobs/get_run/compare_runs/attribute_run），薄封装 + 稳定错误码；
  `scripts/mcp_server.py` 为 stdio 入口（LLM_EVAL_ROOT 指定仓库根）。
- 契约测试：真实子进程 initialize → tools/list → tools/call 全链路；
  端到端：MCP 工具发起 → 后台执行 → 轮询终态 → 取回结果。

### 11.3 后续阶段（未开始）

Phase 2 单租户线上 MVP（FastAPI + Worker + PostgreSQL + 对象存储，HTTP Connector）→
Phase 3 多租户与连接器生态（RBAC/RLS/配额）→ Phase 4 远程 Streamable HTTP MCP
（OAuth 2.1 + scope）→ Phase 5 生态（Agent/多轮/多模态评测、CI 门禁）。
关键安全红线：生产禁用共享进程内模式（inprocess 仅限本地可信环境）；
不接受任意路径/URL；预算超限硬停止；Judge 不可信数据边界。

### 11.4 Phase 2.5：可靠性加固 + 访问控制地基（已完成，2026-09-13）

- **可靠性**（对齐服务化审查 H3/N1/H5 的可测部分）：
  - Judge 调用异常隔离：engine/runner 单条记录记 `judge_error`，评分崩溃不拖垮整批评测；
  - run_id（uuid）入文件名与 summary，消除同秒并发覆盖；
  - 成本账本 v1：`llm.chat` 支持 `on_usage` 回调与超时（120s），LLMJudge 聚合
    `total_usage`，RagJudgeProfile 透传，summary 输出 `llm_usage`；
- **访问控制地基**：
  - tenants/api_keys 表（Key 只存 sha256，明文一次性返回）；幂等键作用域改为租户内
    （unique index (tenant_id, idempotency_key)，迁移先于索引）；
  - 运行产物按租户物理分目录 `runs/tenants/<tenant_id>/`，local 租户沿用历史目录；
  - 按 id 读取统一校验归属，查不到一律 NOT_FOUND（不泄露存在性）；
  - HTTP API 全部 /v1/* 要求 Bearer Key（401），/api/health 免鉴权；MCP 本地模式
    走默认租户 local 不受影响；`scripts/create_tenant.py` 引导创建/吊销；
- **CI**：GitHub Actions（pip install → pytest → MCP 可用性检查）。
- 测试基线：**102 通过 / 3 跳过**；MCP 可用性检查 14/14。
- 后续：Phase 2 完整版（PostgreSQL/对象存储/OAuth）→ 远程 Streamable HTTP MCP →
  连接器生态。本阶段诚实边界：SQLite 单文件、单进程假设；租户隔离为目录与查询级，
  RLS 级隔离待 PG 落地。
